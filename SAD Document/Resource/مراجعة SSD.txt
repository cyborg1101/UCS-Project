2. نقاط القوة الرئيسية في الـSSD
من أقوى الأشياء الموجودة في التصميم:
Modular Monolith
النظام مصمم كـModular Monolith مع فصل واضح بين الوحدات.
كل Module يمتلك بياناته ومنطقه، مع وجود Kernel مشترك للوظائف الأساسية.
Database
التصميم يعتمد على:
• PostgreSQL
• Database واحدة
• Schema منفصلة لكل Module
• Tenant isolation باستخدام المفاتيح/السياق وليس فصل Database لكل Tenant.
Module Ownership
القاعدة الأساسية:
كل Module يمتلك بياناته، ولا يسمح للـModules الأخرى بالقراءة المباشرة من Schema الخاصة به.
والتواصل يتم من خلال:
• API Contracts
• Events
• Read Projections عند الحاجة
مع منع الـcross-schema joins المباشرة.
Cache
تم تصميم Redis باستخدام Namespace/Key isolation.
مثلًا:
{tenant}:{module}:{resource}:{id} 
بحيث لا تستطيع وحدة قراءة Cache الخاصة بوحدة أخرى.
وفي نفس الوقت توجد مساحة مشتركة:
common 
للبيانات العامة التي يسمح بمشاركتها.
والـlive exam state والإجابات لا تعتمد على Redis كـcache.

4. أهم الـExam Flow
الـExam FSM هو:
DRAFT ↓ REQUESTED ↓ SCHEDULED ↓ READY ↓ LIVE ↓ ENDED ↓ GRADING ↓ GRADED ↓ PUBLISHED 
عملية START وEND system-only.
عند بداية الامتحان:
exm.ExamSessionStarted.v1 
ويتم فتح المراقبة في PRC.
وعند النهاية:
exm.ExamSessionEnded.v1 
مع Auto-submit للطلاب الذين لم يسلموا.
5. Idempotency
الـSSD يحتوي على Idempotency paths مهمة، منها:
PUT /exm/submissions/:id/answers 
لحفظ إجابات الامتحان.
وكذلك:
POST /prc/submissions/:id/events 
لأحداث الـIntegrity.
و:
POST /att/sessions/:id/uploads 
ويتم استخدام:
Idempotency-Key 
مع UUIDv7 يتم توليده من الـclient وحفظه محليًا قبل الإرسال.
وهذا مهم جدًا أثناء الامتحانات لأن الشبكة قد تعيد إرسال نفس الطلب.
6. تحديد أثقل وحدات النظام أثناء الامتحان
في البداية تم تحديد ثلاث وحدات مرشحة للضغط العالي:
• EXM — Exam Sessions
• PRC — Integrity / Anti-Cheating
• ATT — Attendance
لكن تم تصحيح هذا الاستنتاج.
ATT ليست Hot Path رئيسية للامتحان
لأن تسجيل الحضور حسب طريقة تشغيل النظام يتم:
طالبًا بطالب أثناء دخول الطلاب إلى القاعة.
وبالتالي لا توجد نفس الـconcurrency الموجودة في:
• حفظ الإجابات
• submission
• exam state
• integrity events
لذلك تم استبعاد ATT من كونها وحدة تستحق Rust فقط بسبب ضغط الامتحان.
7. القرار النهائي بالنسبة لـRust
تم تثبيت القرار على:
EXM + PRC
أي:
EXM — Exam Sessions
وهي أهم وحدة في الـhot path بسبب:
• Answer saves
• Submissions
• Autosave
• Exam session state
• Exam start/end
• عدد كبير من الطلبات المتزامنة.
PRC — Integrity / Anti-Cheating
لأنها تعمل بالتوازي مع الامتحان وتتلقى:
• Integrity events
• Device events
• Monitoring data
• Anti-cheating signals
وبالتالي فإنها أيضًا جزء من الـexam hot path.
القرار المعماري
Rust is used for the two highest-concurrency examination hot-path modules: EXM (Exam Sessions) and PRC (Integrity / Anti-Cheating).
أما باقي الـModules فتظل NestJS/TypeScript، ولا يتم نقلها إلى Rust إلا إذا أظهرت الـprofiling أو الـload testing حاجة فعلية لذلك.
8. لماذا Rust مهم هنا؟
تم توضيح أن Rust لا يعني تلقائيًا استهلاك RAM أقل.
الفائدة الأساسية في هذه الحالة هي:
• High concurrency
• Async processing
• Low runtime overhead
• Efficient memory management
• High throughput
• التحكم الأفضل في concurrency
• تقليل الضغط على NestJS في الـhot path
لكن Rust وحده لا يحل المشكلة.
إذا كان هناك:
• Query سيئة
• Connections كثيرة
• Allocations غير ضرورية
• Payloads ضخمة
• سوء إدارة للـconcurrency
فإن Rust لن ينقذ النظام.
لذلك:
Rust + Architecture جيدة + Database tuning + bounded concurrency + Load Testing
هي التركيبة المهمة.

15. الاستنتاج الأهم حول Rust
تم تصحيح الفكرة من:
"Rust يحل مشكلة RAM"
إلى:
Rust يحل جزءًا كبيرًا من مشكلة الـconcurrency والـCPU والـthroughput في الـexam hot path، وليس 80% من RAM حرفيًا.
إضافة Rust إلى EXM + PRC تجعل النظام أفضل في التعامل مع:
• آلاف الطلبات المتزامنة
• Answer saves
• Integrity events
• Submission bursts
• Exam start/end
• High concurrency
لكن RAM لا تزال تعتمد بشكل كبير على:
• PostgreSQL
• Node/NestJS
• Worker
• Redis
• Connection pools
• Background jobs
• OS overhead
16. النقطة التي وصلنا إليها في النهاية
الفكرة الأساسية أصبحت:
إذا كانت EXM وPRC مصممتين جيدًا بـRust، فقد تم حل جزء كبير من مشكلة الـhot path والـconcurrency.
ثم يصبح الجزء المتبقي متعلقًا بدرجة كبيرة بـجودة الكود والتنفيذ.
أي أن المعادلة أصبحت تقريبًا:
Architecture + Rust Hot Paths + PostgreSQL Optimization + Connection Management + Bounded Concurrency + Good Code + Load Testing = Exam Capacity 
وليس:
RAM فقط = عدد الطلاب 
17. النقاط التي تحتاج حل ومعالجة
P0 — يجب حلها قبل تثبيت الـArchitecture
1. Canonical Module Map
يجب إنشاء جدول واحد رسمي يحدد:
• كل Module
• اسمه الرسمي
• schema
• owner
• dependencies
• events
• APIs
• read projections
حتى لا تظهر أسماء مختلفة لنفس الوحدة بين BRD وSSD.
2. حسم قاعدة Cross-Schema Access
يجب تثبيت القاعدة رسميًا:
No direct cross-schema reads/joins. 
وتحديد الحالات الاستثنائية بدقة:
• API Contract
• Event
• Read Projection
• Materialized View
خصوصًا الـDashboard والـReporting.
3. مراجعة Tenant Isolation
خصوصًا:
• DSH
• Materialized Views
• Read Projections
• Queries
• RLS
والتأكد أن Tenant A لا يمكن أن يرى بيانات Tenant B بأي مسار.
ويجب تحويل هذا إلى Automated Isolation Tests.
4. BRD ↔ SSD Traceability
عمل Matrix تربط:
BRD Requirement ↓ Function ↓ Module ↓ API/Event ↓ Database ↓ Test 
وهذه من أهم الأشياء التي سترفع جودة التوثيق من ممتاز إلى مستوى احترافي جدًا.
18. P1 — مشاكل تحتاج حسم قبل التنفيذ النهائي
5. مراجعة [افتراض-SD]

[افتراض-SD] 
يجب تصنيفه:
• Confirmed
• Pending
• Rejected
• Converted to Decision
حتى لا تبقى افتراضات داخل التصميم النهائي.
6. تثبيت Ownership للـCache
يجب توثيق:
• من يكتب كل key
• من يقرأه
• هل هو module-private أم common
• من يستطيع invalidation
• naming convention
مع تثبيت:
common 
للبيانات المشتركة فقط.
7. مراجعة FKs وIndexes
خصوصًا في:
• EXM
• PRC
• ATT
• PostgreSQL hot tables

8. Security Threat Model

• Tenant breakout
• IDOR
• Replay attacks
• Duplicate submissions

21. القرار الحالي للـExam Architecture
حتى هذه اللحظة، القرار الأكثر وضوحًا هو:
Exam System │ ┌──────────┴──────────┐ │ │ EXM PRC Rust Hot Path Rust Hot Path │ │ └──────────┬──────────┘ │ PostgreSQL │ باقي الـModules NestJS/TS 
والهدف ليس استخدام Rust في أكبر عدد من الوحدات، وإنما:
استخدام Rust فقط حيث يوجد أعلى concurrency وأعلى ضغط أثناء الامتحان.
وهذا يجعل القرار هندسيًا بدل أن يكون مجرد اختيار تقني.
الخلاصة النهائية
الـSSD في وضعه الحالي قوي جدًا، وتقييمه التقريبي:
8.9/10
ولا يحتاج إعادة بناء.
أهم ما يحتاجه الآن هو:
• إزالة التناقضات.
• تثبيت ownership والقواعد.
• ربط BRD بالـSSD بشكل traceable.
• تأكيد Tenant Isolation.
• تثبيت Cache Isolation.
• تثبيت EXM + PRC كـRust hot paths.
• تحسين PostgreSQL والـconnection management.
• ضبط Redis وBullMQ.
• عمل Threat Model.
• عمل Load Test حقيقي حتى 2,000 طالب.
والنقطة الأهم:
بعد نقل EXM وPRC إلى Rust، لا ينبغي أن يكون التركيز التالي على نقل المزيد من الوحدات إلى Rust. التركيز يجب أن ينتقل إلى جودة التنفيذ، PostgreSQL، concurrency control، memory management، والـload testing.
لأن إثبات أن النظام يتحمل 2,000 طالب فعليًا لن يأتي من لغة البرمجة وحدها؛ سيأتي من القياس تحت الحمل الحقيقي.
